# ADR-032: Stable Public Identifiers and Recovery-Safe Identity Boundaries
**Date**: 2026-05-27
**Status**: Proposed
**Decision Owner**: Catown Runtime

---

## Context

Catown currently uses a mix of identifier classes across runtime, chat, monitor, approval, and recovery paths:

- internal relational IDs such as `task_runs.id`, `chatrooms.id`, `messages.id`
- lineage or correlation IDs such as `client_turn_id`, `tool_call_id`, `flow_id`
- dedupe or replay helpers such as `request_key`
- opaque continuation tokens such as `resume_token` and tracked `run_shell` `token`

This was workable while most flows stayed within one process and one short-lived request. It becomes unsafe when the same entities are used across:

- restart recovery
- approval replay / continuation
- delegated task reconstruction
- monitor lookup and timeline stitching
- background `run_shell` tracking

The immediate incident that triggered this ADR was a recovery-safety concern:

1. recovery entry correctly resumes a `TaskRun` by `task_run.id`
2. recovery execution later rehydrates prompt context by reading recent messages from `task_run.chatroom_id`
3. `chatrooms.id` is an internal SQLite row ID, not a stable public identity
4. SQLite on this machine currently runs with `PRAGMA foreign_keys = 0`
5. if stale rows survive or a chat identity is reused, recovery can read the wrong live chat context

This exposed a broader design issue:

**Catown does not yet clearly separate internal row identity from stable cross-process public identity.**

Several fields also currently carry more semantic weight than they should:

- `client_turn_id` is used as a UI lineage anchor, but some paths also use it for runtime reconstruction
- `request_key` is used as a dedupe key, but could be mistaken for an entity identity
- `workflow_id` is a semantic name, not a durable primary identity

We need one consistent policy for uniqueness and identity boundaries before more recovery and replay features are added.

---

## Decision

### 1. Keep integer primary keys for internal relational storage

Catown will continue to use existing integer primary keys as the internal relational join keys for core tables:

- `chatrooms.id`
- `messages.id`
- `task_runs.id`
- `approval_queue_items.id`
- `pipeline_runs.id`
- `pipeline_stages.id`
- `stage_runs.id`
- related business tables

These IDs remain valid for:

- local joins
- ORM relationships
- internal admin and monitor queries
- compact storage and predictable ordering

Catown will **not** do a full "replace all PKs with UUID" migration.

### 2. Add stable public IDs to recovery-relevant entities

Catown will add a second identifier layer: a stable opaque public ID.

Each recovery-relevant entity must have a `public_id` (UUID text) that is:

- generated by the backend
- immutable after creation
- unique at the table level
- safe to persist into payloads, logs, monitor views, and recovery checkpoints

Phase 1 required entities:

- `chatrooms.public_id`
- `messages.public_id`
- `task_runs.public_id`
- `approval_queue_items.public_id`
- `pipeline_runs.public_id`
- `pipeline_stages.public_id`

Phase 2 recommended entities:

- `stage_runs.public_id`
- `assets.public_id`
- `decisions.public_id`

### 3. Snapshot parent public IDs into long-lived child records

When a child object can outlive, replay, or recover independently from its parent, Catown will persist the parent's public identity snapshot on the child.

Required examples:

- `task_runs.chatroom_public_id`
- `messages.chatroom_public_id`
- `approval_queue_items.chatroom_public_id`
- `approval_queue_items.task_run_public_id`
- `pipeline_runs.task_run_public_id`
- `pipeline_stages.pipeline_run_public_id`

These snapshot fields are used for:

- restart-time consistency checks
- stale-row detection
- replay safety
- auditability of "which exact parent identity did this child belong to when created"

### 4. Recovery and replay must validate identity boundaries before using live context

Any recovery, replay, or continuation path that reconstructs execution from persisted state must validate stable parent identity before reading mutable live state.

For example:

- orchestration recovery must verify the `TaskRun` still belongs to the same `chatroom_public_id` before reading recent chat messages
- approval replay must verify `ApprovalQueueItem.chatroom_public_id` and `task_run_public_id` match current rows before continuing
- delegated task reconstruction must not rely on `client_turn_id` alone

If validation fails, Catown must stop recovery and surface an explicit identity-mismatch failure instead of proceeding with best-effort reconstruction.

### 5. Reclassify soft identifiers by purpose

Catown will explicitly treat the following identifier classes differently:

- **public entity identity**
  - `public_id`
  - stable, opaque, globally unique within its entity table
  - valid for recovery, replay, deep links, API exposure

- **internal row identity**
  - integer PKs
  - valid for joins and local implementation details

- **lineage / correlation IDs**
  - `client_turn_id`
  - `tool_call_id`
  - `flow_id`
  - used for display stitching and within-turn correlation
  - not valid as authoritative recovery identity

- **dedupe / idempotency keys**
  - `request_key`
  - valid only for semantic dedupe
  - not an entity identity

- **resume / continuation tokens**
  - `resume_token`
  - tracked `run_shell` `token`
  - opaque bearer-style continuation handles
  - must remain unique and unguessable

### 6. `client_turn_id` remains a frontend/backend lineage anchor, not a stable entity ID

`client_turn_id` will remain in the system because it is useful for:

- optimistic UI stitching
- correlating a user send with runtime cards
- grouping assistant output and monitor entries

But Catown will stop treating `client_turn_id` as sufficient by itself for:

- delegated task reconstruction
- background failure terminalization
- recovery object lookup
- cross-chat runtime ownership decisions

Those paths must move to `public_id`-anchored lookup, optionally with `client_turn_id` as an auxiliary signal.

### 7. Enforce uniqueness and foreign-key discipline more strictly

In addition to adding public IDs, Catown will tighten the persistence contract:

- enable SQLite foreign keys at connection setup
- add unique indexes for `public_id`
- add a unique index for `approval_queue_items.resume_token`
- keep `request_key` as a dedupe key, not a globally unique entity key
- consider partial uniqueness for pending approval dedupe semantics where supported by migration strategy

## Rationale

### Why not replace every primary key with UUID?

A full PK replacement would create wide migration risk without solving the core issue by itself. The main problem is not "integers are bad"; it is "internal row IDs are being trusted outside their intended boundary."

Keeping integer PKs preserves:

- existing joins and relationships
- current monitor and ORM behavior
- simpler incremental migration

Adding `public_id` solves the actual problem:

- stable identity across recovery and replay
- explicit separation between storage key and public identity
- safer persistence of references in payloads, checkpoints, and logs

### Why add both `public_id` and parent snapshots?

A child row that only stores `chatroom_id=3` cannot prove that row `3` still represents the same chat identity that existed when the child was created.

Persisting:

- `task_runs.chatroom_id`
- `task_runs.chatroom_public_id`

lets Catown ask:

"Does this row still point at the same chat identity, or only the same current integer row?"

That is the key safety property recovery paths need.

### Why keep `client_turn_id`?

`client_turn_id` is still useful as a UI and event-lineage anchor. The problem is not its existence. The problem is treating it as stronger than it is.

The frontend currently generates values like:

- `turn-<timestamp>-<random>`

This is acceptable for stitching cards and optimistic UI, but it is not a backend-owned immutable entity identifier.

### Why classify `request_key` separately?

`request_key` represents semantic dedupe, not identity.

Examples:

- "the same blocked tool request should not create multiple pending approvals"
- "the same pipeline gate should not create duplicate queue rows"

Those are idempotency concerns, not object identity concerns.

## Design

### 1. Public ID shape

Each `public_id` field should:

- use backend-generated UUID text
- be stored as `String`
- be `NOT NULL`
- have a unique index

Recommended format:

- canonical UUID string or compact hex UUID

Catown does not need globally sortable UUID variants for this phase. Opaque uniqueness is sufficient.

### 2. Recovery-safe lookup pattern

Recovery and replay services should adopt this lookup pattern:

1. resolve the primary entity by internal PK when already held locally
2. validate persisted `public_id` snapshots against the current parent rows
3. only then read mutable live state such as chat messages, runtime cards, or project context

If validation fails:

- do not continue
- append a failure event describing the mismatch
- surface the mismatch in monitor and API responses

### 3. API exposure pattern

Existing routes may continue to accept integer IDs during transition, but responses should begin including `public_id` for recovery-relevant objects.

Transition target:

- monitor and chat payloads expose both `id` and `public_id`
- internal admin routes may continue to use `id`
- any future resume/replay deep-link or externalized workflow route should prefer `public_id`

### 4. Delegation and approval safety rules

Delegation:

- a delegated task card may still display `client_turn_id`
- the actual persisted task linkage should include `task_run_public_id`
- reconstruction should first match `task_run_public_id`, then validate `chatroom_public_id`

Approval replay:

- queue items should carry `task_run_public_id` and `chatroom_public_id`
- replay must fail closed if the current row mapping disagrees

Background `run_shell`:

- tracked process handles should continue to use opaque `token`
- records should also persist `task_run_public_id` so follow-up does not rely only on `task_run_id` or `client_turn_id`

---

## Non-Goals

This ADR does not require:

- replacing all integer PKs with UUID PKs
- globally unique IDs across every table using one shared namespace
- changing all existing route path parameters in one release
- redesigning every monitor projection in the same migration

## Implementation Notes

### Migration ordering

Recommended safe order:

1. add nullable columns
2. backfill values
3. add unique indexes
4. switch write paths to populate the new fields
5. switch recovery/replay validation paths
6. make fields non-null where appropriate

### Failure behavior

Identity mismatches should fail closed with explicit reasons such as:

- `chatroom_identity_mismatch`
- `task_run_identity_mismatch`
- `pipeline_run_identity_mismatch`

These reasons should be visible in:

- task-run events
- approval resolution/replay logs
- monitor projections
- API error details where appropriate

### Testing priorities

Highest-priority tests:

- startup recovery does not read a mismatched chat context
- delegated task reconstruction does not cross-match another run by shared `client_turn_id`
- approval replay refuses to continue if queue item parent snapshots disagree
- delete/recreate chat scenarios do not attach stale recoverable state to the new chat identity

---

## Consequences

### Positive

- recovery and replay gain explicit identity safety boundaries
- Catown stops depending on mutable or weak identifiers for long-lived execution state
- monitor and audit payloads become easier to correlate across restarts
- future external APIs can expose stable object references without leaking internal row semantics

### Negative

- schema and payload complexity increases
- create paths must now populate more identity fields consistently
- migration and backfill work touches several core runtime tables
- some existing helper code that assumes `client_turn_id` is enough will need refactoring
